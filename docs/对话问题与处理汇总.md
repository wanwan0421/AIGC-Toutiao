# 对话问题与处理汇总

> 截至 2026-10-25。合并了对话中的重复追问；“已实现”指当前代码或已有评测文档能找到对应实现，不等于已经完成真实浏览器、跨设备和线上验收。“待验证”表示尚无足够证据证明问题在实际使用中消失。

## 一、产品定位与写作风格

| 问题 | 原因或结论 | 现有处理方法与状态 |
| --- | --- | --- |
| “内容增长”是什么意思？ | 指让内容更容易被发现、互动和再次使用；搜索、订阅、关注流、收藏、分享、回复和举报属于社区能力。它不等同于单纯增加 AI 生成量。 | 这些是后续社区功能方向，本轮写作风格项目未把它们一并实现。 |
| “创作者经验 Skill”为何出现读者和旅行规划？ | 早期方案把 Skill 理解为供读者调用的旅行方法，与用户要的创作者写作方法不一致。 | 产品范围已改为创作者本人使用：从旧文提炼结构、语气、叙述视角和主题写法，辅助写新文章；不做读者侧旅行 Agent。 |
| Skill 由谁创建，怎样与“风格库”配合？ | 它不是作者手写的可执行程序。AI 从作者选择的已发布文章提炼候选写法，作者编辑、确认后才生效。 | 使用一份可版本化的写作风格档案，包含主题写法；新稿结合本次素材、需求和已确认的风格生成。风格档案不应存入旧文的具体经历、地点或价格作为新事实。 |
| 是不是创新点？如何守住真实经验？ | 价值在于复用作者自己的表达方法，不能因为生成量增加而编造经历、降低经验密度。 | 首版以作者本次提供的素材和本人旧文为输入；经历采集助手、事实依据检查和图片理解不在首版范围。 |
| 通用写法与按主题写法是否都要选？ | 两套入口容易重复，作者难以理解区别。三篇厦门文章只足以说明厦门主题的写法，不能代表作者所有题材。 | 创作入口以“关闭”或“选择主题写作风格”为主；档案内部可以保留共享规律，界面优先呈现主题风格。 |
| 新文章如何进入某份主题风格？ | 仅用文章标签或关键词自动归类不可靠，可能把校园文章学进旅游风格。 | 当前发布后自动学习有时间、公开状态和文章长度等条件，并生成待确认候选；**明确的主题归属规则仍需完善**，宜由作者设置主题或确认新文章归属。来源修改、删除或下线会触发版本失效控制。 |
| 风格档案为什么重复、难读？ | “通用/主题”内容重叠，七个长文本字段平铺，术语和说明文字过多。 | 页面已调整为摘要、写作节奏、表达习惯、来源与版本等区域；仍需用真实作者做可读性验收，继续压缩重复字段和提示文案。 |
| 七阶段进展如何判断？ | 单元测试和类型检查只能证明部分约束与逻辑，不能代替真实生成和盲测。 | 阶段 1–6 有对应实现及自动化检查；阶段 7 已准备盲测工具与记录文档，旅游、研究生生活各 10 份未参与建档的新素材和作者盲选仍待完成。见 [SKILL_PLAN.md](../SKILL_PLAN.md) 与 [阶段 7 记录](evaluation/writing-style-stage7.md)。 |

## 二、编辑器、图片与页面交互

| 问题 | 具体原因 | 现有处理方法与状态 |
| --- | --- | --- |
| “补充信息”标题、输入框与原表单不一致，还有多余限制提示 | 新增字段使用了不同的字重、背景和帮助文案。 | 改为沿用原表单视觉样式；补充信息保留简短示例占位，不常驻显示 TXT/MD 数量、大小和图片用途说明。实际输入限制仍由服务端校验。 |
| “＋”菜单、参考旧文弹窗关不掉或两侧同时开 | 菜单开关只由按钮控制；两处“参考旧文”各用独立布尔值。 | 统一为当前打开位置（左侧、右侧或关闭），点击外部及按 Escape 收起。仍需浏览器交互回归。 |
| 写作风格放在左侧表单导致拥挤、标题只剩一个字 | 左栏宽度有限，列表和多层滚动挤压可读空间；风格属于生成选项，不是填写需求。 | 入口移至中央编辑区顶部，与状态和保存同栏，使用紧凑的“写作风格”下拉选择。 |
| 我的写作风格页面与平台风格不统一 | 页面增加副标题和大量说明卡片，与作品管理等页面的大标题和列表布局不同。 | 已调整页面层级和卡片布局；用户仍认为内容平铺、难懂，需继续做作者可读性验证。 |
| 封面上传慢、裁剪拖动抖动、正文小图太窄 | 上传时若串行做内容审核会阻塞预览；裁剪坐标和显示缩放若不同步会抖动；正文图片原有宽度可能按固有尺寸显示。 | 上传只做类型、大小、解码、尺寸和安全重编码；封面在前端预览并拖动图片选取主体，只保存裁剪后的封面副本。正文小图按比例放大至正文区域宽度。裁剪手感仍需真机验收。 |
| 图片如何存储，是否需要上传即审核？ | 文件安全检查与内容合规审核是两个环节；上传即调模型会拖慢交互。 | 图片通过资产存储链路保存，上传环节做文件安全处理；用户点“内容审核”时才对封面和正文配图做内容审核。具体存储部署安全性需按实际环境核查。 |
| 保存无反馈，或提示“正文与富文本显示内容不一致” | Tiptap 的 JSON、HTML、纯文本若在转换或自动保存时不同步，会被服务端一致性校验拒绝。 | 统一正文序列化和可见文本计数，保存状态在界面反馈；若仍复现，应记录该草稿的三种正文表示和保存请求定位。 |
| 图片下出现“全线思路小节后”等字样 | 配图 `position` 是插入槽位元数据，曾被拼进可见正文。 | 保留 `position` 用于图文匹配和进度；渲染正文时不输出槽位标签。 |
| 生成过程中只有固定状态，完成后聊天里没有 AI 回复 | 原流程关注编辑器回填，缺少阶段事件和最终助手消息持久化。 | 后端按需求分析、写作、视觉规划、图片生成发进度；前端展示阶段、Skill 和图片完成数。终态存简短助手回复，结束后隐藏临时进度；不展示模型内部推理。 |
| 删除作品后列表仍显示 | 删除后的本地列表可能被旧请求、焦点刷新或缓存结果覆盖。 | 删除成功即从本地列表移除，并用已删除 ID 阻止旧请求把它放回；返回页面时重新拉取目录。需回归快速删除、切页及慢请求竞争场景。 |
| 聊天历史失效或不显示 | 对话 ID 与草稿关联可能丢失或合并；历史请求失败若被当作空列表，会看似“记录没了”。 | 当前代码补了对话 ID 保存/恢复、按 ID 读取、服务端合并处理及“重试加载”提示；已有对应单元测试。此前没有保存关联 ID 的孤立记录不能保证自动找回，仍需跨草稿、刷新和跨设备实测。 |

## 三、内容审核与质量评估

| 问题 | 具体原因 | 现有处理方法与状态 |
| --- | --- | --- |
| 审核通过后又提示图片未审核 | 文字结论与图片资产状态曾分开更新；只看文章状态会出现“文字通过、图片 pending”。 | 一个前端可见的异步内容审核任务内并行处理文字和图片；全部通过后才给当前文章“审核通过”，并刷新素材列表。 |
| 文字和图片如何并行，单图失败如何重试？ | 多图串行会叠加延迟，整篇重试会重复已完成调用。 | 文字仍执行规则预检加 LLM 复审；未命中缓存的图片走多模态结构化审核，图片有限并发（代码中为 2），逐项保存结果。网络、限流或结构化失败保留待重试状态；复核时复用已完成项。 |
| 图片审核规则要与文字完全相同吗？ | 两种模态的证据不同，不能共用一套逐字提示词；通过门槛应一致。 | 共用平台内容安全标准，图片提示词只判断可见证据，文字保留规则预检。模型支持图像与结构化输出不等于整篇合并请求一定更快、更稳。 |
| 为何缓存要用图片 SHA-256，而不只用素材 ID？ | ID 标识资产记录，不能证明实际审核过的字节仍相同；裁剪、副本或存储变化会改变图片内容。 | 审核时计算文件 SHA-256 并纳入记录；相同图片字节可以复用图片结果，正文变化不必重审图片。当前按用户要求暂不把模型标识纳入图片缓存键；规则变更仍需专门的失效机制。 |
| 同一文章没有修改，能否复用成功或失败的结果？ | 单凭“文章 ID”无法区分标题、正文和图片变化。 | 使用当前内容指纹匹配历史审核记录，未变化时复用结论；图片也核对审核状态。若显示“结果已失效”，应检查指纹组成、图片哈希和保存时序。 |
| 改了内容，为什么还显示“安全审核通过”？ | 页面曾保留旧审核卡片，未立即按本地编辑状态判失效。 | 当前前端会比对本地与已审核内容，失效时隐藏通过卡片并显示“审核结果已失效”；服务端以当前内容指纹决定能否发布。此改动仍需浏览器回归。 |
| 审核通过但质量评估禁用，或质量报告沿用旧文字 | 前端状态可能未刷新；质量结果若按旧正文或尚未保存的内容命中缓存，会得到过期报告。 | 质量按钮以服务端工作流状态为准；质量评估按标题和正文指纹缓存。编辑后须先保存，再请求质量评估，并核对返回记录的指纹。 |
| 第一遍图片审核为何耗时几分钟，单图实测却只要 6.76 秒？ | 6.76 秒仅是一次单图模型调用；真实任务还包含队列、文字审核、多图、下载、结构化校验、重试和状态回写。 | 并行文字和图片、图片有限并发、逐图缓存与失败项重试；用任务和模型调用日志拆分各段耗时，不能以单图时延推算整篇总耗时。 |
| 要不要合并成一次多模态审核？ | 合并可减少请求数，但一处失败会使整篇重试，且失去逐图缓存的收益。 | 现阶段采用拆分并行；后续用相同样本比较总时长、成功率和费用，再决定是否合并。 |

## 四、生成性能、成本与任务状态

| 问题 | 具体原因 | 现有处理方法与状态 |
| --- | --- | --- |
| 为什么强模型生成图文仍慢，官网首 Token 却很快？ | 官网 TTFT 是单请求首输出指标；完整图文还要经历排队、需求分析、正文、视觉规划、图片生成、重试和回填。深度思考及长结构化输出也增加时延。 | 流水线记录阶段名、首 Token、总耗时、重试、Token、模型和价格快照；限制各阶段字段长度、输出 Token 与配图数量。先看分段瓶颈再改模型。 |
| 当前模型是否匹配？关闭思考或换模型是否有效？ | Seed-Evolving 具备项目所需的结构化和图像理解能力，但“能力匹配”不代表在此任务上成本、速度最优。 | 通过 `AI_CONTENT_PRODUCTION_THINKING_MODE=enabled/disabled` 对照；设置必须写在实际加载的 API/Worker 环境文件并重启，仅改 `.env.example` 不生效。模型更换须比较真实任务日志与成稿质量。 |
| 关闭思考后的第一次生成为什么报失败，第二次却成功？ | 截图只能证明前端曾显示失败，不能单凭它判定 Ark、结构化校验、任务重试或前端状态哪一环出错。 | 先按任务 ID 核对 `AiJob` 终态、失败阶段和 `AiCallLog`；此前针对首次失败误报已调整前端终态显示。再次复现需保留同一任务的日志，不能把两次任务混为一次。 |
| A/B 怎样做才严谨？ | 相同用户需求可做实用对比，但随机生成、素材版本、提示词、风格版本和图片任务会干扰结论。 | 固定代码、模型、提示词、素材、风格版本及图片配置，只切换思考模式；比较端到端时间、各阶段 TTFT、重试、Token 与费用，同时盲评文章质量。单轮结果不宜归因为思考开关。 |
| `AiCallLog` 字段为什么不一致？ | 不同生成路径、图片调用和独立任务有不同阶段，旧记录与新记录的日志形态也不同；空值不必然是漏记。 | 当前表有可选 `stage`、首 Token、思考模式、成本等字段；应统一 `scene` 与 `stage` 含义，按调用类型填适用字段，未知费用留空，不用零掩盖缺失。历史日志不能凭空补全。 |
| 出现 `AI_CONCURRENCY_LIMIT`、Ark stream 失败，前端还“正在思考” | 聊天父任务派生子任务时可能碰到并发配额；Ark 流中断或任务终态未同步，会留下临时消息和按钮状态不一致。 | 子任务配额须按父子关系计算，终态由服务端任务记录驱动；成功、失败、取消都收束成助手回复并释放按钮。Ark 错误应保留可定位的任务 ID、阶段和重试记录；异常场景仍需端到端演练。 |
| `Redis wait failed; using PostgreSQL polling: Connection is closed` 是失败吗？ | 等待任务通知的 Redis 连接关闭，服务端退回数据库轮询。 | 这是降级日志，不单独表示生成失败；需结合任务终态和 worker 日志判断。若频繁出现，再查 Redis 生命周期和连接复用。 |
| 前端和数据库为何经常状态不一致？ | 本地临时状态、自动保存、异步任务、轮询和服务端写回并存，容易出现旧请求覆盖新结果。 | 以持久化任务和工作流状态为最终依据，前端在关键操作后重新获取，并对失效审核、失败终态和聊天消息做收束；慢请求竞争仍是回归重点。 |
| AMap 报 `CUQPS_HAS_EXCEEDED_THE_LIMIT / 10021` | 高德附近地点接口超过调用频率或配额，和 Ark 生成、内容审核不是同一个故障。 | 控制附近地点请求频率、缓存结果并提示限流；核查高德配额及密钥配置。 |

## 五、开发环境与验收

| 问题 | 具体原因 | 现有处理方法与状态 |
| --- | --- | --- |
| `AiController` 找不到 `WritingSkillService` | Nest 模块没有向控制器所在模块导出或导入该 provider。 | 当前 `WorkflowModule` 提供并导出 `WritingSkillService`，`AiModule` 导入 `WorkflowModule`；服务启动仍以实际运行验收为准。 |
| 3000/3002 端口占用、Prisma DLL 被占用 | 已运行的 Web/Worker/API 占用端口或 Windows 下的 Prisma 引擎文件。 | 曾按用户授权停止相关进程并重试客户端生成；用户随后要求只由自己启动服务。此文档整理不启动或停止任何服务。 |
| 单元测试如何验收，端到端和界面验收怎么做？ | 单元测试覆盖函数、服务与状态分支，无法证明真实浏览器交互、数据库迁移、Ark 调用及跨设备恢复。 | 先用类型检查与测试验证逻辑，再以真实 API/Worker/Web 环境检查选文建档、风格生成、文件上传、审核、发布、自动学习和历史恢复；阶段 7 用未参与建档的素材盲评。 |
| 数据库怎样保持严谨、简洁？ | 把每个 UI 状态或流水线阶段都做成重复列，会产生多个“真相来源”。 | 复用现有文章、资产、任务与版本关系；风格档案保留必要版本/来源关系；调用日志只记录统一的调用事实、可选阶段、价格快照和真实缺失值。 |

## 当前仍需重点验收

1. 实际浏览器中的菜单关闭、封面裁剪、正文图片宽度、删除后列表刷新、审核失效提示和聊天历史恢复。
2. Ark/Redis 故障、任务取消和并发配额下，前端消息、按钮与数据库终态是否一致。
3. 主题归属规则：新发布文章进入哪一份主题风格，不能仅由标签推断。
4. 阶段 7 的 20 份新素材、两组生成和作者盲评；目前只有评测工具，尚无可宣称的效果结论。
