# 今日头条创作服务平台

> 本笔记以当前工作区代码为准，重点说明内容创作、认证、草稿、AI 任务、审核、榜单和部署。按当前范围，本文不讨论提示词管理页面、模板版本、实验和测试回放等管理能力。

# 零、项目概述

## 1、项目简介

本项目是一个面向内容创作者的 AI 辅助创作平台，覆盖选题与对话辅助、图文生成、富文本编辑、素材管理、内容安全审核、质量评分、发布流转、榜单和数据分析。

它不是一个“请求模型后把文字显示出来”的简单 Demo。当前项目的核心是把长耗时 AI 操作做成可持久化任务，并将“模型已经生成结果”和“结果已经可靠写入文章”拆成两个不同阶段。

## 2、当前系统架构

```text
浏览器（Next.js）
  ├─ 普通业务请求：Bearer Access Token
  ├─ 刷新会话：HttpOnly Refresh Cookie + CSRF Token
  └─ AI Job 事件：fetch + ReadableStream 解析 SSE
             │
             ▼
NestJS API
  ├─ 用户、内容、草稿、素材、审核、榜单接口
  ├─ 创建 AiJob + AiJobEvent + AiJobDispatch（同一事务）
  ├─ Outbox Dispatcher 投递 BullMQ
  └─ 从 PostgreSQL 回放事件，Redis Streams 负责唤醒等待中的 SSE
             │
             ▼
Redis / BullMQ ─────► 独立 Worker
                         ├─ 执行 AI 工作流
                         ├─ 写检查点、进度和部分结果
                         ├─ 响应真正的 AbortSignal 取消
                         └─ 进入 succeeded 或 awaiting_commit
             │
             ▼
PostgreSQL
  ├─ 核心业务事实
  ├─ AI 任务、事件、Outbox、检查点
  └─ 内容、草稿、素材关系、审核和评分记录
```

### 前端：Next.js + React + TypeScript + Tailwind CSS

- App Router 组织首页、创作中心、内容、数据分析、榜单、话题和用户页面。
- TipTap 负责富文本编辑，正文同时维护纯文本、HTML 和 JSON 三种形态。
- `@aicp/shared` 共享前后端业务类型，统一内容状态、AI Job 状态、SSE 事件和结构化错误。
- `useAiJob` 统一封装任务启动、事件消费、断线重连、页面刷新后重新挂载、取消和终态清理。
- 浏览器不直接连接 PostgreSQL 或 Redis；所有数据都经由 NestJS HTTP/SSE 接口访问。

### 后端：NestJS + TypeScript + Prisma

- Controller 负责协议与鉴权，Service/Capability/Agent/Workflow 分担业务编排和模型能力。
- Prisma 管理关系数据、事务、索引和迁移。
- API 进程只负责接收请求、持久化任务、分发任务和提供 SSE，不直接执行长耗时 AI Job。
- 独立 Worker 通过 Nest application context 复用既有能力，但不启动 HTTP API。

### PostgreSQL、Redis 与 BullMQ

- PostgreSQL 是业务事实来源，保存内容、草稿、任务当前状态和可精确回放的任务事件。
- Redis 保存短期认证会话、缓存和短期对话上下文，也是 BullMQ、取消通知以及 SSE 唤醒通道的基础设施。
- BullMQ 负责持久队列、Worker 消费、失败重试和 stalled 任务恢复。
- Redis Streams 中的任务事件副本不是最终数据源；Redis 不可用时，SSE 会退化为 PostgreSQL 轮询。

## 3、项目亮点

1. **后台任务可靠执行。**任务先在 PostgreSQL 中落库，再通过事务 Outbox 投递 BullMQ，避免“数据库已创建任务但队列投递失败”造成任务丢失。
2. **执行恢复与监听恢复相互独立。**BullMQ/Worker 恢复后台计算，`useAiJob` 恢复浏览器对任务的观察；SSE 重连不会重新创建或重新执行任务。
3. **结果回填有持久化确认。**图文和单图生成先进入 `awaiting_commit`，浏览器把完整编辑器快照原子保存后，任务才变成 `succeeded` 并产生 `done`。
4. **取消不是只断开 SSE。**取消先落库，再通知 Worker，中止模型请求、图片生成和远程文件下载；旧 Worker 也无法覆盖取消状态。
5. **规则审核与语义审核结合。**规则阶段使用词库、正则、组合规则和上下文白名单，随后由 LLM 复核并合并结果。
6. **结构化输出有确定性校验。**模型输出经过 JSON 解析、归一化和字段校验，不直接把任意模型文本写入编辑器。

## 4、当前边界

- 同一个编辑器页面通过 `activeOperation/isBusy` 限制同时进行一个会改写编辑器的 AI 操作；这不是整个用户、整个系统或多用户之间只能调用一个模型。
- `useAiJob` 本身同一时刻只维护一个活动 SSE 控制器。新监听会停止旧监听，但只有显式调用 `cancelJob` 才会取消后台任务。
- `sessionStorage` 能支持同一标签页刷新恢复，但不保证关闭标签页或浏览器后仍保留。后台任务仍会继续运行；当前还缺少“按用户列出未完成任务”的恢复入口。
- 草稿保存目前没有服务端乐观锁。两个浏览器同时编辑同一篇文章时是后写覆盖先写；`clientHash` 只被记录，没有用于条件更新或冲突检测。
- 当前生产 Nginx 的通用 `/api/` 位置仍开启 `proxy_buffering`，可能影响 SSE 的实时到达。应为 SSE 路由单独关闭缓冲，或由响应增加 `X-Accel-Buffering: no`。

# 一、如何完整启动项目

## 1、准备依赖

在项目根目录安装依赖：

```bash
npm install
```

根据 `apps/api/.env.example` 配置数据库、Redis、认证密钥和模型服务。生产环境必须提供可靠的 `AUTH_TOKEN_SECRET`。

## 2、启动 PostgreSQL 与 Redis

```bash
docker compose -p aicp up -d
```

开发 Compose 使用：

- PostgreSQL 14，宿主机端口 `5432`；
- Redis 7，宿主机端口 `6379`；
- Redis 开启 AOF；
- PostgreSQL 数据库名为 `AIGC-Toutiao`，默认用户名和密码都是 `aicp`。

停止服务：

```bash
docker compose -p aicp stop
```

## 3、执行数据库迁移

首次启动或 Prisma schema 发生变化时执行：

```bash
npm run db:migrate
```

需要演示数据时可执行：

```bash
npm run db:seed
```

`prisma generate` 只重新生成 Prisma Client；`prisma migrate dev` 会生成并应用开发迁移；生产环境应使用 `prisma migrate deploy` 应用已提交的迁移。

## 4、分别启动 API、Worker 和 Web

需要三个持续运行的终端：

```bash
npm run dev:api
```

```bash
npm run dev:worker
```

```bash
npm run dev:web
```

- Web 默认监听 `3000`。
- API 默认监听 `3001`。
- Worker 是独立进程；开发环境如果没有启动 Worker，AI Job 会排队但不会被执行。


## 2、当前主要数据模型

### 用户和内容

- `User`：用户账号与基础资料。
- `UserPreference`：创作偏好。
- `Content`：文章当前版本和发布状态。
- `Draft`：编辑中的云端草稿快照。
- `ContentVersion`：显式内容更新和回滚使用的历史版本。
- `ContentReaction`、`ContentComment`、`UserFollow`：互动关系。
- `UserActionEvent`：浏览、点赞、收藏、评论等行为事件。

### 素材、审核和评分

- `Asset`：素材元数据，文件本体不存入数据库；`generationKey` 用于 AI 图片幂等。
- `ContentAsset`：内容与素材的多对多关系和排序。
- `AuditRecord`：内容安全审核结果；`aiJobId` 可唯一关联一次后台任务。
- `QualityScore`：质量评分结果；`aiJobId` 同样用于重试幂等。
- `AiCallLog`：模型调用摘要、耗时和结果记录。

### AI 会话与可靠任务

- `AiConversation`、`AiMessage`：创作对话归档。
- `AiJob`：任务当前状态和最终结果，一行代表一个任务。
- `AiJobEvent`：任务的追加式事件日志；自增 `id` 同时作为 SSE 事件 ID。
- `AiJobDispatch`：事务 Outbox，记录任务是否已投递队列。
- `AiJobCheckpoint`：步骤级检查点，唯一键是 `(jobId, stepKey)`。

## 3、`AiJob` 与 `AiJobEvent` 的区别

`AiJob` 描述“任务现在是什么状态”，例如：

```text
queued → running → awaiting_commit → succeeded
                 └───────────────→ failed
queued/running/awaiting_commit ──→ cancelled
```

`AiJobEvent` 描述“任务一路发生过什么”，例如 `snapshot`、`progress`、`partial`、`warning`、`result_ready`、`done`、`error`。

两者都需要保留：

- 查询当前状态只需读 `AiJob`；
- 网络断线后精确补发过程事件依赖 `AiJobEvent`；
- 事件清理后，终态仍可由 `AiJob` 合成当前快照或终态响应。

### 三个 ID 不要混淆

- `AiJob.id` / `jobId`：任务标识，也被用作 BullMQ 的自定义 `jobId`。
- `AiJobEvent.id`：PostgreSQL 全局自增主键，也是 SSE 的 `id:` 和前端保存的 `Last-Event-ID`。
- Redis Stream ID：Redis 内部用于阻塞读取和唤醒的游标，不是业务续传 ID，前端也不会保存它。

# 三、前端实现

## 1、异步闭包与草稿快照

React 异步回调容易捕获旧 state。项目通过 `snapshotRef.current` 在真正保存时读取编辑器最新快照，而不是依赖定时器创建时的闭包值。

保存流程是：

1. 输入事件只负责安排本地或云端保存。
2. 定时器触发后调用 `snapshotRef.current()`。
3. 快照包含标题、纯文本、HTML、TipTap JSON、标签、素材和发布设置。
4. `saveLockRef` 阻止同一个 Hook 内重叠的云端保存请求。

`saveLockRef` 解决的是前端重复请求和旧响应覆盖风险，不是数据库死锁，也不能解决两个浏览器的并发编辑冲突。

## 2、`void` 的正确含义

`void` 既是 JavaScript 一元运算符，也是 TypeScript 类型关键字。

```ts
void autoSaveDraft();
```

这里表示调用异步函数但有意忽略它返回的 Promise 值，常用于事件处理器或定时器中。它不会自动捕获 Promise rejection；如果函数内部没有处理异常，仍应使用 `catch`：

```ts
void autoSaveDraft().catch(reportError);
```

## 3、认证：内存 Access Token + HttpOnly Refresh Cookie

当前项目不是 localStorage Token，也不是“Access Token 也放在 HttpOnly Cookie 中”的纯 Cookie 鉴权。实际方案是：

### Access Token

- 登录、注册或刷新后在响应 JSON 中返回。
- 前端只保存在 `auth-token-store.ts` 的模块内存中，不写 `localStorage`、`sessionStorage` 或普通 Cookie。
- 有效期 15 分钟。
- 普通业务请求通过 `Authorization: Bearer <token>` 携带。
- 普通业务请求默认 `credentials: "omit"`，不依赖浏览器自动携带认证 Cookie。

### Refresh Token

- 只写入 `aicp.refreshToken` HttpOnly Cookie，前端 JavaScript 读不到。
- Cookie 路径限定为 `/api/auth`，`SameSite=Lax`，生产默认 `Secure`，有效期 7 天。
- Redis 保存 Refresh Session；Redis key 使用 Refresh Token 的 HMAC 摘要。
- 刷新时删除旧 Session 并创建新 Session，即 Refresh Token rotation。

### CSRF 防护

普通业务接口使用 Bearer Header，不会仅因为浏览器带上 Cookie 就通过鉴权；CSRF 重点集中在使用 Refresh Cookie 的刷新和退出接口。

当前措施包括：

- 刷新和退出要求 `X-CSRF-Token`；
- CSRF Token 由当前 Refresh Token 派生，保存在前端内存中；
- 校验 `Origin` 白名单和 `Sec-Fetch-Site`；
- CORS 使用明确 Origin；
- mutation 接口拒绝常见 simple content type，素材上传例外。

该方案降低了长期 Token 被 XSS 持久窃取的风险，但内存 Access Token 在当前页面运行期间仍可被恶意脚本读取，因此 CSP、依赖治理和输出清洗仍然重要。

### 自动刷新与退出

- 需要鉴权但内存中没有可用 Access Token 时，前端先用 Refresh Cookie 换取新 Access Token。
- 收到 401 时只尝试刷新一次，再重放原请求。
- `refreshAccessTokenPromise` 和浏览器 Lock API 避免同页或多标签页同时轮换同一个 Refresh Token。
- `BroadcastChannel` 同步同源标签页的内存会话更新和退出事件。
- 退出时后端删除 Refresh Session，将当前 Access Token 的 `jti` 写入 Redis 黑名单，并清除 Refresh Cookie；前端同时清空内存 Token 和保存的 AI Job 会话。

## 4、草稿与版本管理

### 三层保存

1. **浏览器 localStorage**：输入后 800ms 防抖保存，断网时仍可工作。
2. **PostgreSQL**：输入后 3 秒防抖进行云端保存，另有 30 秒定时兜底。
3. **Redis**：数据库事务提交成功后缓存最新 `Draft`，TTL 为 24 小时，加快读取。

云端自动保存不是“只写 Draft”。`ContentDraftPersistenceService` 在一个 PostgreSQL 事务中：

1. 校验素材归属；
2. 创建或更新 `Content`；
3. 更新正文的纯文本、HTML、JSON 和标签；
4. 必要时重置审核相关状态；
5. 替换 `ContentAsset` 关系；
6. upsert `Draft`；
7. 事务提交后再刷新 Redis 草稿缓存。

### 正文三种形态

- `body`：纯文本，是 AI、审核、评分、搜索和字数统计的语义来源。
- `bodyHtml`：详情和预览的渲染缓存。
- `bodyJson`：TipTap 可编辑文档，用于完整恢复富文本结构。

### 回显优先级

编辑器初始化时会读取内容详情、云端草稿和本地草稿，并比较保存时间。本地快照更新时优先恢复本地编辑；否则使用云端草稿/内容。最终通过 TipTap 编辑器引用应用 JSON 或 HTML，而不是直接操作 `contentEditable` DOM。

### 两个浏览器同时编辑

当前服务端更新没有 `revision`、`updatedAt` 条件写或 `If-Match`，因此是 last-write-wins。`ContentVersion` 能回滚显式更新留下的版本，但自动保存本身不会为每次变动建立可靠冲突分支。

如果要真正支持协同编辑，至少应增加：

- 内容修订号或 ETag；
- `UPDATE ... WHERE id=? AND revision=?`；
- 冲突时返回 409 和服务端最新快照；
- 前端提供覆盖、合并或另存副本；
- 实时多人协作则需要 OT/CRDT，而不只是保存锁。

## 5、`useAiJob`：启动、监听和断线恢复

### 启动

`runJob(start, handlers)` 的主要步骤：

1. 中止当前 Hook 旧的 SSE 控制器；
2. 调用启动接口创建后台任务；
3. 得到 `AiJobSnapshot` 和 `jobId`；
4. 将 `jobId/type/contentId/lastEventId/pendingCommit` 等写入 `sessionStorage`；
5. 调用 `consumeJob` 监听这个已有任务。

中止旧控制器只会停止浏览器监听，不会自动取消旧后台任务。需要停止后台执行时必须调用 `cancelJob`，它会请求 `/api/ai/jobs/:id/cancel`。

### 为什么不用原生 EventSource

原生 `EventSource` 不能设置任意 `Authorization` 请求头，而当前业务鉴权必须携带内存中的 Bearer Access Token。因此前端使用：

```text
fetch(Authorization + Last-Event-ID)
  → response.body.getReader()
  → TextDecoder
  → 按空行切分 SSE block
  → 解析 id/event/data
```

这仍然是 SSE 协议，只是客户端不是浏览器原生 `EventSource`。

### 精确续传与去重

- 服务端把 `AiJobEvent.id` 写为 SSE `id:`。
- 前端成功处理事件后，才在 `onEventProcessed` 中保存这个 ID。
- 重连时通过 `Last-Event-ID` Header 发送给服务端。
- 前端用数值顺序判断 `event.id > lastEventId`，过滤重复事件。
- 如果 `onResultReady` 或其他异步回调失败，事件 ID 不会前移；下次重连仍会重放该事件。

这属于“至少一次投递”：尽量不丢事件，但允许重复。业务副作用必须幂等，不能假设每个事件只到达一次。

### 网络断开恢复

`consumeJob` 在一个 `while (!signal.aborted)` 中循环：

1. 带当前 `Last-Event-ID` 建立一次物理 SSE 连接；
2. 处理直到服务端结束、连接断开或请求抛错；
3. 对不可重试的 400/403/404/422 等错误停止循环；
4. 对网络错误、429、502、503、504 等可重试错误查询一次 `GET /ai/jobs/:id`；
5. 如果任务已经终态，直接执行终态处理；
6. 否则按指数退避等待后重新连接；
7. 429/503 的 `Retry-After` 优先，最长等待 5 分钟。

退避不会因为连接建立、heartbeat 或无 ID 的合成 snapshot 立即清零。只有成功处理比建连起点更新的持久事件，或者连接稳定 30 秒，才重置重连次数。

### 页面刷新恢复

网络断开时 React 和内存变量仍在，所以当前 `consumeJob` 可以原地循环。页面刷新会销毁整个 React 进程，必须走另一条路径：

1. 启动任务后已把必要信息写入 `sessionStorage`；
2. 编辑器重新初始化后按任务类型和 `contentId` 寻找可恢复记录；
3. 调用 `resumeJob(jobId)` 查询服务端当前状态；
4. 非终态则携带保存的事件 ID 重新挂载 SSE；
5. 已终态则直接执行 `onDone/onError`；
6. 任务成功、失败、取消或退出登录后删除记录。

页面刷新不是“根据 contentId 重新创建任务”。`contentId` 只用于从本标签页的多个记录中挑选对应 `jobId`，真正查询和续传仍以 `jobId` 为准。

### 组件卸载清理

组件卸载时会 `abort()` 当前前端 Fetch/SSE，并移除事件监听器和定时器，避免卸载后的组件继续 setState。它不会取消 Worker 正在执行的任务，这是有意区分“我暂时不看”和“我要求停止任务”。

## 6、AI 结果如何回填到编辑器

图文生成和单图生成是浏览器回填型任务，采用两阶段完成：

1. Worker 生成结果后把 `AiJob.result` 保存到 PostgreSQL；
2. 任务进入 `awaiting_commit`，进度为 95；
3. 创建带持久 ID 的 `result_ready`，此时没有 `done`；
4. 编辑器用 AI 结果和当前编辑器状态生成一份完整快照；
5. 同一快照既用于更新 UI，也作为 `/api/ai/jobs/:id/commit-result` 的提交内容；
6. 服务端在一个事务中保存 `Content`、`Draft`、`ContentAsset`、`AiJob` 和 `done`；
7. 任一步骤失败全部回滚，任务仍可再次提交。

前端在调用提交接口前把完整 `pendingCommit` 写入 `sessionStorage`。如果响应丢失或页面刷新，会重发相同请求。服务端使用 `resultEventId + payloadHash` 判断幂等：

- 相同事件、相同 payload 重复提交，返回已保存内容；
- 同一任务已用不同内容提交，返回冲突；
- `resultEventId` 不是该任务的 `result_ready` 事件，拒绝提交。

`onDone` 不再负责插入正文或图片，只负责终态 UI、重新加载服务端已保存内容和清理任务记录。

## 7、网络协议与结构化错误

项目主要使用两类协议：

- 普通 JSON HTTP：内容、草稿、素材、榜单、任务创建/查询/取消/提交。
- SSE：创作对话流和 AI Job 单向事件流。

AI Job SSE 与普通创作对话 SSE 不同：

- `streamCreativeChat` 直接流式返回 `meta/delta/skill/done/error`，本身不做 PostgreSQL 事件回放；当路由器决定执行长 Skill 时，它会创建一个 AiJob。
- `streamAiJobEvents` 监听已经存在的后台任务，支持 PostgreSQL 回放、Last-Event-ID、重连和页面恢复。

后端统一错误响应：

```ts
type ApiErrorResponse = {
  statusCode: number;
  code: string;
  message: string;
  retryable: boolean;
  requestId: string;
  retryAfterMs?: number;
  details?: Record<string, unknown>;
};
```

前端 `ApiError` 保留这些字段。没有 HTTP 响应的 Fetch `TypeError` 被映射为可重试 `NETWORK_ERROR`。请求 ID 会回写到响应头，未知 500 不向客户端暴露堆栈。

## 8、LCP 与前端性能现状

当前 Next.js 配置已经包含：

- `next/image` 的 WebP/AVIF 与尺寸配置；
- 静态资源长期缓存；
- 压缩、ETag、keep-alive；
- 常用依赖的按需导入；
- CSP 和基础安全响应头；
- Nginx gzip 和静态资源缓存。

但不能笼统写成“LCP 已经完全优化”。仓库中 2026-06-11 的 Lighthouse 三次桌面报告为 95～96 分，LCP 约 0.86～0.91 秒；三次移动报告为 52、69、71 分，LCP 约 3.48～5.50 秒。说明桌面表现较好，移动端仍需继续优化图片、首屏数据、JavaScript 执行和网络环境。

# 四、后端实现

## 1、AI 编排模式：语义路由 + 确定性工作流

项目虽然使用了 `Agent`、`Capability` 和 `Skill` 命名，但不是多个独立智能体自由通信、长期自治的“智能体团队”或“共享状态群聊”。更准确的定义是：

```text
语义路由 Agent
  → 选择 chat / 局部编辑 / 追问 / 一个 Skill
  → SkillExecutor 执行固定业务流程
  → Capability 组合一个或多个专用 Agent/服务
  → Workflow 负责权限、状态和持久化
```

- 路由器只看到可用 Skill 的 key、name 和 description，一次最多选择一个 Skill。
- 完整图文生产的需求分析、正文、视觉规划、输出归一化和图片生成顺序是预先定义的。
- 各 Agent 没有独立任务队列，也不会相互自由发消息或共同修改数据库。
- 因此它更接近“中央路由 + 分层确定性流水线”，而不是自主多智能体协作。

## 2、一键图文生成

当前入口是：

```http
POST /api/ai/creative/direct-generate/jobs
```

它不再同步等待完整图文。完整链路是：

1. API 在事务中创建 `AiJob(queued)`、初始 `snapshot` 和 `AiJobDispatch(pending)`。
2. 事务提交后立即尝试投递 BullMQ；Redis 不可用时由 Outbox 后续恢复。
3. Worker 领取任务并写入新的 `runToken`，状态变成 `running`。
4. `SkillExecutor` 运行内容生产线。
5. 草稿和每张图片写步骤检查点。
6. Worker 写 `result_ready` 并进入 `awaiting_commit`。
7. 浏览器原子提交完整编辑器快照。
8. 保存成功后任务才进入 `succeeded` 并写 `done`。

### 工作流步骤

1. 需求分析：整理主题、受众、风格、视角和素材。
2. 文章草稿：生成标题、候选标题、Markdown 正文、标签和大纲。
3. 视觉规划：生成封面建议和正文图片槽位。
4. 输出归一化：修正结构并形成统一结果。
5. 确定性校验：验证必要字段并标准化结果。
6. 图片生成：封面和正文图片最多 2 个并发，按文章长度限制正文配图数量。

### 检查点与幂等

- 草稿：`draft`
- 封面：`image:cover`
- 正文图：`image:inline:{slotId/index}`
- 单图：`single-image`
- 服务端工作流结果：`workflow-result`

Worker 重试时先读取检查点，只补做缺失步骤。图片素材还使用 `generationKey = jobId + stepKey` 的唯一约束；即使供应商已返回而 Worker 随后崩溃，也能避免重复创建业务素材记录。

## 3、结构化输出

项目没有仅依赖 TypeScript 类型，因为类型在运行时不能约束模型文本。实际做法是：

1. 要求模型输出 JSON；
2. `parseJsonObject` 先尝试直接 `JSON.parse`，失败时再提取首个对象片段；
3. 各 Agent 把未知数据显式转换为字符串、数组和对象；
4. 一键生成在归一化前后都执行 `validateDirectGenerateResult`；
5. 最终仍不合法则任务失败，而不是把残缺数据写入编辑器。

`validateDirectGenerateResult(candidate)` 当前会：

- 要求 `title` 和 `bodyMarkdown` 非空；
- 要求 `tags` 至少一个，并去掉重复 `#`、补成统一 `#tag`、去重；
- 要求 `titleCandidates`、`imagePrompts`、`outline` 的原始值是数组；
- 丢弃没有有效标题的标题候选；
- 丢弃没有有效图片描述的图片项，为位置提供默认值；
- 将图片 `slotId` 清洗为安全字符、限制长度并保证本次结果内唯一；
- 如果正文缺少对应图片槽位标记，则按段落补入；
- 删除正文开头与标题完全重复的一行；
- 清理空大纲项，并把 `imageAssets` 初始化为空数组。

它目前不检查标题长度、正文最小长度、候选标题最小数量，也不做 JSON Schema/Zod 级的深层字段约束。因此应称为“确定性预校验与归一化”，不能夸大成完整的业务质量验证器。

## 4、可靠 AI Job：Outbox、BullMQ 与 Worker

### 为什么需要事务 Outbox

如果先写数据库再投队列，进程可能在两步之间崩溃；如果先投队列再写数据库，Worker 又可能找不到任务。当前创建任务时在一个 PostgreSQL 事务内写入任务、初始事件和 Outbox，然后再投队列。

Dispatcher 每 2 秒领取待投递记录，使用 `FOR UPDATE SKIP LOCKED` 避免多个 API 实例重复领取。BullMQ 的自定义 `jobId` 固定为 `AiJob.id`，重复 `queue.add` 不会创建第二个相同任务。

Outbox 解决的是“投递前后短暂故障”，BullMQ 解决的是“已入队任务的消费、重试和 Worker 故障恢复”。API 不再在启动时扫描 `AiJob` 并直接重跑，也不再通过进程内 `setTimeout` 执行长任务。

### 重试和旧 Worker 竞争

- 默认 Worker 并发 2。
- 每个 BullMQ Job 最多 3 次执行，指数退避起点 2 秒。
- 只有结构化错误的 `retryable=true` 才进入正常重试。
- 每次执行生成新的 `runToken`。
- 进度、部分结果、检查点和终态写入都要求 `status=running AND runToken=当前值`。
- 条件更新影响 0 行时，旧 Worker 不得继续写事件或成功状态。

这使系统能够接受至少一次执行，但通过数据库条件写和唯一约束保证业务效果幂等。

### 真正取消

取消接口先在 PostgreSQL 事务中：

1. 将 `queued/running/awaiting_commit` 原子更新为 `cancelled`；
2. 清空 `runToken`，写错误码 `JOB_CANCELLED` 和终态事件；
3. 取消未投递 Outbox。

事务提交后再：

- 尝试移除 waiting/delayed BullMQ Job；
- 发布 Redis `ai-job:cancel` 通知；
- 唤醒 SSE。

Worker 收到通知后调用 `cancelJob`，并每 1 秒查询本进程活动任务的数据库状态作为 Pub/Sub 丢失的兜底。AbortSignal 会继续传给模型 `fetch`、图片生成和远程文件下载。即使外部供应商没有及时中止，取消已经清除了 `runToken`，旧执行也不能写成成功。

## 5、PostgreSQL 回放与 Redis 等待如何衔接

一次 SSE 循环的顺序是：

1. 从 PostgreSQL 查询 `AiJobEvent.id > Last-Event-ID`，每批最多 500 条；
2. 按 ID 顺序全部发送；
3. 查询 `AiJob` 当前状态；
4. 如果终态则发送/合成终态事件并关闭；
5. 如果仍在运行，用 Redis `XREAD BLOCK 15000` 等待新事件通知；
6. 被唤醒后回到第 1 步，再从 PostgreSQL 读取真实事件；
7. Redis 不可用时每 3 秒轮询 PostgreSQL；
8. 等待周期结束后发送无 ID 的 heartbeat。

Redis 的价值是避免每个 SSE 连接持续高频查询 PostgreSQL，同时让新进度尽快到达。它并不负责精确回放：Redis Stream 只保留约 1000 条、TTL 24 小时，而 PostgreSQL `AiJobEvent` 才是续传事实来源。

## 6、事件保留与维护任务

独立 Worker 使用 BullMQ Job Scheduler 每 24 小时运行维护任务：

- `awaiting_commit` 超过 7 天未提交时转为 `failed`，错误码为 `RESULT_COMMIT_TIMEOUT`；
- 只删除完成超过 30 天的 `succeeded/failed/cancelled` 任务事件；
- 运行中和待提交任务的事件不会按普通保留策略删除；
- 每批默认 1000 条，单次最多 100000 条；
- BullMQ 自身只保留最近 1000 条 completed 和 5000 条 failed 记录。

## 7、内容安全审核

### 规则预检

规则引擎不是把所有风险词拼成一个巨型正则，而是混合使用：

1. `SafetyRuleLoader` 递归读取 `.txt` 词库，过滤无效短词、去重并缓存在进程内；
2. 普通词库通过大小写归一化后的 `indexOf` 循环查找全部命中位置；
3. 手机号、身份证、银行卡、邮箱、外链、联系方式等使用专用正则；
4. 赌博词+联系方式、涉毒词+交易词、色情词+价格/联系方式等使用邻近组合规则；
5. 组合词最大距离 80 字，证据片段最多 120 字，每类最多保留 8 项；
6. 科普、反诈、禁毒等上下文白名单会降低部分中风险规则置信度，但不会压低高风险项；
7. 重叠结果按风险级别、置信度和证据位置去重合并。

词库只在首次加载时读磁盘，所以不会每个请求重新读文件。不过当前扫描普通词库的最坏复杂度近似“词条数 × 文本长度”，词库继续扩大或需要扫描长文档时仍可能变慢。可根据压测结果升级为 Trie/Aho-Corasick、分词索引或 Worker 预编译结构，而不是盲目堆正则。

### LLM 复核与结果合并

规则结果会作为结构化上下文交给 `SafetyReviewAgent`。`SafetyResultMerger` 再合并规则和 LLM：

- 同类、同字段、重叠证据合并；
- 高风险规则、强正则和组合规则可直接保留；
- 普通词库的中风险命中更依赖 LLM 类型/分数确认；
- 白名单语境且 LLM 不确认的项可被抑制；
- LLM 判断存在阻断风险但没有返回有效片段时，会生成 fallback 风险项；
- 最终有 medium/high 风险项即不通过；不通过时再尝试合规改写。

### 当前评测应该怎样表述

`docs/evaluation/high-risk-eval-samples.json` 是 30 条人工构造的回归集：14 条 `expectedHighRisk=true` 的高危样本，16 条低/中风险对照样本。高危由样本中的预期风险等级、类别和 rationale 人工标注，不是线上投诉或审核结论自动推导。

同一数据集上：

- 纯规则基线：TP=6、FN=8、FP=0、TN=16，高危召回率 42.86%，精确率 100%，准确率 73.33%。
- 完整规则+LLM 链路：TP=9、FN=5、FP=1、TN=15，高危召回率 64.29%，精确率 90%，准确率 80%，F1=75%。

因此“召回提升 21.4%”的准确说法是**提升约 21.43 个百分点**（64.29%-42.86%），如果计算相对提升则是约 50%（21.43/42.86）。30 条人工样本只能作为回归证据，不能代表线上总体效果。

## 8、审核、评分与发布状态

- 提交审核只做安全审核，不再同时做质量评分。
- 安全审核通过时内容变成 `approved`，不通过变成 `rejected` 并可返回改写建议。
- 质量评分只允许在 `approved/updated/published/scheduled` 状态上执行，并要求当前内容存在仍然有效的安全审核通过记录。
- 内容发生安全敏感修改时，审核有效性会被重置，防止拿旧审核结论发布新正文。
- 发布前再次由 `ContentReviewPolicyService` 校验当前内容是否可发布；审核控制在后端，不依赖前端按钮状态保证安全。
- 前端当前使用 Job 版本的审核和评分接口；代码仍保留部分同步兼容接口，不应把兼容入口误认为主链路。

## 9、图片持久化

图片二进制不存 PostgreSQL。当前实现使用本地存储适配器：

1. 模型返回 data URL 或临时远程 URL；
2. 后端下载或解码文件；
3. 保存到 `uploads/ai-images`；
4. `Asset` 只记录稳定访问 URL、storageKey、MIME、大小、来源和生成元数据；
5. 内容通过 `ContentAsset` 关联素材。

生产 Compose 为 API 和 Worker 挂载同一个 `uploads` volume，否则 Worker 保存的图片 API 无法读取。当前不是 OSS/CDN；迁移对象存储时只需新增 Storage Adapter，业务层不应依赖本地绝对路径。

AI 图片生成和远程下载都接收同一个 AbortSignal。`generationKey` 的唯一约束负责重复执行去重。当前 AI 生成图片会直接标记为 approved，这是一项需要结合业务风险继续评估的策略，不能描述为已经完成独立视觉安全审核。

## 10、榜单、话题和热度

榜单只从 `published + public` 内容中选候选，并排除平台官方话题账号内容。默认预取 500 条，最多 1000 条，计算分数后再分页。

三种榜单：

- `recommended`：质量分 100%。
- `hot`：近 7 日行为 55% + 累计互动 25% + 浏览 20%。
- `viral`：近 7 日行为 40% + 累计互动 15% + 浏览 10% + 质量 35%。

近 7 日事件权重：浏览 1、点赞 2.5、收藏 3、评论 3；取消点赞 -2.5、取消收藏 -3。累计浏览和互动先通过 `log1p` 压缩，再按候选集合归一化，避免头部大数值完全压制其他内容。

榜单 Redis 缓存 TTL 当前是 30 秒，不是 5 分钟。话题榜根据公开文章标签聚合热度。`ContentHeatScoreService` 还会用固定上限归一化出展示用 `heatScore`，它与某次榜单请求的相对排序分数不是同一个概念。

# 五、部署与工程化

## 1、生产 Compose 服务

当前 `docker-compose.prod.yml` 包含 7 个服务：

1. `postgres`
2. `redis`
3. `migrate`
4. `api`
5. `worker`
6. `web`
7. `nginx`

`migrate` 是一次性服务，先应用数据库迁移；API 和 Worker 等待它成功。长任务必须由独立 `worker` 服务执行，不能只部署 API 和 Web。

## 2、健康检查与依赖

- API readiness 检查 HTTP 健康接口和 PostgreSQL，不因短时 Redis 故障直接失败，因为任务可以先进入 Outbox。
- Worker `/ready` 同时检查 PostgreSQL 和 Redis。
- Worker 与 API 使用同一镜像、环境变量和 uploads volume。
- Redis 开启 AOF；PostgreSQL、Redis 和 uploads 都使用命名卷。

## 3、Nginx 和 Next.js

- Nginx 反向代理 `/api/` 到 API，其余请求到 Next.js。
- 上传文件缓存 30 天，Next 静态资源缓存 1 年。
- Next.js 使用 standalone 输出，生产镜像无需完整源码运行。
- 当前部署只监听 HTTP 80，仍需在真实生产环境增加 HTTPS、证书续期和 HTTP→HTTPS 跳转。
- AI Job SSE 应增加单独 Nginx location 并关闭代理缓冲，避免通用 `/api/` 缓冲策略延迟事件。

# 六、常见问题

## 1、为什么完整图文生产要拆成多个步骤

因为写作、结构、视觉规划和图片生成的失败模式不同。拆分后可以逐步校验、单独记录进度、只重试缺失步骤，并让用户提前看到草稿或图片部分结果。它是固定流水线，不是让多个 Agent 无限制互相迭代。

## 2、后台已经负责任务恢复，为什么前端仍要断线恢复

两者恢复的对象不同：

- 后台恢复保证“任务最终有人继续算”，由 Outbox、BullMQ、Worker 和检查点负责。
- 前端恢复保证“用户重新看见同一任务的进度和结果，并完成必要回填”，由 `sessionStorage`、Last-Event-ID、SSE 重连和 `commit-result` 负责。

没有前端恢复，任务可能在后台成功，但页面不知道结果；没有后台恢复，前端再怎么重连也只能一直看到 queued/running。

## 3、什么是幂等

同一个动作执行一次或重复执行多次，最终业务结果一致，就叫幂等。

项目中的例子：

- BullMQ `jobId = AiJob.id`，重复投递不产生第二个队列任务；
- `(jobId, stepKey)` 唯一检查点避免重复完成同一步；
- 图片 `generationKey` 避免重复素材；
- `runToken + status` 条件更新阻止旧 Worker 写终态；
- 相同 `resultEventId + payloadHash` 重复提交只返回已经保存的内容；
- Last-Event-ID 只在事件业务处理成功后推进。

## 4、为什么编辑器限制同时一个 AI 操作

限制范围是当前编辑器 Hook/标签页的共享写入面，不是同一个用户的全局配额，更不是多用户只能调用一次 LLM。

图文生成、局部改写、审核和图片插入可能基于不同正文版本。如果同时回填，容易发生旧结果覆盖新编辑、图片重复插入或审核对象与当前正文不一致。未来若要支持并行，应为每个操作使用独立 Hook/控制器，并给编辑器快照增加 revision 和显式合并策略。

## 5、普通创作对话需要和 AiJob 一样持久化事件吗

不一定。普通对话的 token 流用于即时展示，断线后可以从 PostgreSQL 的会话消息重新加载已归档结果；把每个 token 都保存成 AiJobEvent 成本很高。只有当对话路由到耗时、可产生业务副作用的完整 Skill 时，才创建 AiJob 并进入可靠任务链路。

当前 `streamCreativeChat` 自身没有 Last-Event-ID 精确续传；如果希望断线后继续逐 token 接收，需要另行设计消息级序号、分块存储和重放协议，不能直接声称已经具备。

## 6、项目是否支持 140+ 轮长会话和 Token 降低 30%

当前代码不能支持这个结论。Redis 短期记忆只保留最近 12 条消息、TTL 2 小时；PostgreSQL 会归档完整会话，但模型上下文默认也只读取最近 12 条，并对当前正文做最多约 600 字的摘要。

因此可以说“通过窗口化上下文控制单次请求长度”，但仓库中没有在相同模型、相同任务、相同样本条件下证明 140+ 轮可用或 Token 降低 30% 的评测。若要对外使用这些指标，必须补充固定数据集、基线策略、Token 计量、任务成功率和摘要信息丢失评估。

## 7、当前最值得继续优化的地方

1. 为内容/草稿增加 revision 乐观锁，解决多浏览器覆盖。
2. 为用户提供“未完成 AI 任务列表”，弥补 sessionStorage 在关闭标签页后的恢复边界。
3. 为 Nginx SSE 路由关闭缓冲并做真实断网/代理超时测试。
4. 对灾难性 Redis 数据丢失补充“已标记 dispatched 但队列记录消失”的对账机制。
5. 对大词库做基准测试，必要时用 Aho-Corasick/Trie 替换逐词扫描。
6. 补充 AI 生成图片的视觉安全审核，而不是默认通过。
7. 扩大并分层维护审核评测集，报告置信区间、类别召回和线上分布。
8. 继续优化移动端 LCP，并为生产环境补齐 HTTPS。
